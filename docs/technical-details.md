# Технические детали проекта

Справка для ИИ-агентов (Claude Code и т.п.), которые продолжат работу над
`LadyBugHitTheRoad` — в том числе на другом компьютере, с нуля. Раздел 1 — как
подключиться к проекту агентом. Раздел 2 — как физически устроена разработка
(инструменты, ограничения). Раздел 3 — во что превратилась сама игра
(механики). Раздел 4 — архитектура кода, система за системой.

## 1. Как агенту подключиться к проекту (все варианты)

### Вариант A — MCP-сервер `unity-mcp` (если настроен и работает)
В `~/.claude.json` может быть подключён MCP-сервер:
```json
"unity-mcp": {
  "command": "/Users/<user>/.unity/relay/relay_mac_arm64.app/Contents/MacOS/relay_mac_arm64",
  "args": ["--mcp"]
}
```
Если он поднят и Unity Editor с этим проектом открыт, агенту доступны
инструменты: `Unity_RunCommand`, `Unity_GetConsoleLogs`, `Unity_Camera_Capture`,
`Unity_SceneView_Capture2DScene`, `Unity_SceneView_CaptureMultiAngleSceneView`,
`Unity_AssetGeneration_GenerateAsset`, `Unity_AssetGeneration_GetModels`. Это
потенциально позволяет напрямую видеть консоль/сцену Unity без участия
пользователя.

**Важно:** за всё время разработки этого проекта (десятки итераций правок)
агент **ни разу фактически не использовал** этот MCP-путь — вся работа шла
через Вариант B ниже. Считайте MCP необязательным бонусом, не зависимостью:
если он недоступен, отсутствует в `~/.claude.json`, relay-процесс не
запущен, или инструменты `Unity_*` не появляются в списке — просто
переходите к Варианту B, это штатный, проверенный способ работы.

Как проверить, жив ли MCP: поискать процесс relay (`ps aux | grep relay_mac`)
и/или попробовать вызвать любой `Unity_*`-инструмент. Если не отвечает —
не пытаться чинить/переустанавливать MCP самостоятельно без явной просьбы
пользователя; это внешняя настройка окружения пользователя, а не часть
проекта.

### Вариант B — через файловую систему, без запуска Unity (основной, всегда рабочий)
Пользователь держит Unity Editor открытым на протяжении всей сессии. Из-за
этого агент **не может** сам запускать Unity в `-batchmode` из терминала —
вторая запущенная копия Unity с тем же проектом падает с ошибкой «another
Unity instance is running». Рабочий цикл вместо этого:

1. Агент правит `.cs`-файлы в `UnityProject/Assets/Scripts/` (рантайм-логика)
   и/или `UnityProject/Assets/Editor/SceneSetup.cs` (генератор сцены —
   правится только если меняется состав/расположение объектов на сцене, а не
   только их поведение).
2. Если менялся **только** рантайм-код (`Assets/Scripts/*.cs`, кроме
   `SceneSetup.cs`) — Unity подхватит изменения сама при переключении фокуса
   на Editor (домен перезагрузится, скрипты перекомпилируются). Rebuild
   Scene **не нужен**.
3. Если менялся `SceneSetup.cs` (новые объекты/UI-панели/связи между
   компонентами) — агент обязан попросить пользователя переключиться в
   Unity и выполнить **Tools → Rebuild Scene**. Сам агент этого сделать не
   может — только пользователь, руками, в открытом Editor.
4. Сцена **пересоздаётся с нуля** каждый раз (`BuildScene()` вызывает
   `EditorSceneManager.NewScene(...)` в начале) — она никогда не
   редактируется вручную и не хранится как источник правды. Источник правды —
   код в `SceneSetup.cs`.

Это единственный способ, которым фактически построен весь проект — надёжный
и не требует никакой специальной настройки на новой машине, кроме открытого
Unity Editor у пользователя.

### После правок — как самому проверить, что код не сломан
Агент не может запустить Unity, но может текстово проверить синтаксис:
```bash
python3 -c "
s = open('ПУТЬ/К/Файлу.cs').read()
print(s.count('{')-s.count('}'), s.count('(')-s.count(')'))
"
```
Ноль-ноль не гарантирует компиляцию, но ловит львиную долю опечаток
(незакрытая скобка после большого рефакторинга) до того, как пользователь
увидит ошибку в Unity Console. Практика, которой агент придерживался после
**каждой** правки в этом проекте.

## 2. Инструменты и ограничения разработки

- **`SerializedObject`/`SerializedProperty`** — единственный способ задать
  значения приватных `[SerializeField]`-полей компонентов, создаваемых в
  `SceneSetup.cs` (сам он — Editor-скрипт, лежит в `Assets/Editor/`, не
  попадает в билд). Для `KeyCode`-полей — **обязательно** `.intValue = (int)someKeyCode`,
  не `.enumValueIndex`: порядок объявления констант в `KeyCode` не совпадает
  с их числовым значением, `.enumValueIndex` даст не ту клавишу.
- **`PrefabUtility.SaveAsPrefabAsset`** требует, чтобы любой `Material`,
  на который ссылается объект, был уже сохранён как ассет
  (`AssetDatabase.CreateAsset`) — иначе после сохранения префаба ссылка
  превращается в «битую» (пурпурный материал). Отсюда два похожих хелпера в
  `SceneSetup.cs`: `ApplyColor` (для объектов сцены, не идущих в префаб) и
  `ApplyPersistentColor` (сохраняет материал как ассет — для всего, что
  попадёт в префаб). Игроки и их тени живут прямо в сцене (не в префабах) —
  для них подходит обычный `ApplyColor`/in-memory `Material`.
- **Script execution order через `LateUpdate`** — многопользовательское
  голосование газ/тормоз (и жестовое тоже) полагается на гарантию Unity, что
  все `Update()` всех скриптов кадра отрабатывают раньше любого
  `LateUpdate()` этого же кадра. `SpeedController.LateUpdate()` суммирует
  голоса, поданные за кадр `PlayerController`/`GestureInput` через
  `RegisterAccel()`/`RegisterBrake()`, без явной настройки Script Execution
  Order.
- **Регистронезависимая файловая система macOS** — папки `Assets` и `assets`
  на этой машине физически совпадают. Поэтому сырые исходники арта лежат не
  в `assets/`, а в `RawAssets/` (см. структуру репозитория ниже).
- **Отключение компонента останавливает и `OnTriggerEnter`**, не только
  `Update` — используется намеренно: `PlayerController.enabled
  = false` на стартовом экране/во время паузы/помощи одновременно глушит
  и ввод, и обработку столкновений.

### Сборка билда
`UnityProject/Assets/Editor/BuildScript.cs` → `BuildScript.PerformBuild()`
собирает `Assets/Scenes/Main.unity` в `Builds/LadyBugHitTheRoad.app`
(`BuildTarget.StandaloneOSX`). Вызывается через
`Unity -batchmode -quit -executeMethod BuildScript.PerformBuild` — но, как и
с Rebuild Scene, пока Editor открыт у пользователя, агент не может выполнить
это сам.

### Сторонние CLI-инструменты, использованные при подготовке ассетов
- **`swftools`** (`brew install swftools`), команда `swfextract` — вытаскивание
  растровых спрайтов из `RawAssets/swf/LadybugAdventures.swf` (оригинальная
  Flash-игра, источник стиля дороги/препятствий/декораций).
- **`rsvg-convert`** (`brew install librsvg`) — конвертация скачанных SVG в PNG.
- **Wikimedia Commons API** — источник картинок, которых не было в `.swf`
  (конус, колесо, велосипед, животные и т.п.).

### Быстрый старт на новой машине
1. Установить Unity **6000.0.78f1** (или достаточно близкую 6000.x — если
   версии разойдутся, Unity Hub предложит апгрейд `ProjectVersion.txt`, это
   безопасно).
2. Unity Hub → Open → выбрать именно `lady_bug/UnityProject`
   (не `lady_bug/`).
3. После первого открытия: **Tools → Rebuild Scene** — соберёт
   `Assets/Scenes/Main.unity` с нуля из кода. Без этого шага сцены не будет
   вообще (она не хранится в git/файлах вручную).
4. Play.

## 3. Суть игры

**LadyBugHitTheRoad** — локальный кооперативный (1 или 2 игрока) endless-runner
про божью коровку на дороге с тремя полосами. Игроки делят один мир/дорогу
(не сплит-скрин). Цель: набрать 100 очков за минимальное время, попутно
выполняя трюки.

### Стартовый экран (`StartScreenController`)
Дорога стоит, но не мертва: `SpeedController` держит её на фоновой скорости
(`minSpeed`), дорога и боковые декорации едут, спавнер докидывает только
хорошие объекты (`EntitySpawner.PickPrefab` форсирует good, пока игра не
началась) — фон живой. Игроки не реагируют на ввод до подтверждения.

Три строки меню, между ними ↑/↓ (любые: стрелки/WASD), внутри строки ←/→:
1. **1 ИГРОК / 2 ИГРОКА** — превью вживую: второй жук появляется/исчезает,
   в режиме на одного правый жук встаёт на среднюю полосу.
2. **КЛАВИАТУРА / ДАТЧИКИ / ИМИТАТОР** — выбор источника ввода (раздел про
   жесты ниже). «Датчики» (реальное железо) — заглушка «не реализовано»;
   «Имитатор» — рабочая клавиатурная симуляция сенсоров.
3. **СТАРТ** — газ (I/Shift, любой) подтверждает.

Между заголовком и меню — карусель из 4 страниц (10 сек/страница, по кругу):
Суть игры → Цель → Управление → Трюки.

### Управление в игре — клавиатура
- **Правый игрок**: `← →` полоса, `↑` прыжок, `↓` пригнуться, `I` газ,
  `K` тормоз (раскладка IJKL — тормоз K, не J).
- **Левый игрок**: `A D` полоса, `W` прыжок, `S` пригнуться, `Shift` газ,
  `Ctrl` тормоз.
- Газ/тормоз **независимы и суммируются** каждый кадр
  (`SpeedController.LateUpdate`): оба жмут газ → ускорение вдвое; один газ +
  один тормоз → взаимно гасятся.
- **F1** — пауза + экран помощи с полным текстом управления (см. `HelpController`).
- Держать тормоз 5 сек **всем** активным игрокам сразу (после того как
  скорость уже упала до минимума) → диалог «Закончить игру?» (см. `PauseController`).

### Управление в игре — датчики расстояния / имитатор (`GestureInput`)
По датчику на каждую руку каждого игрока (2 датчика × 2 игрока = 4), каждый
смотрит вертикально вниз на свою руку. Реальное железо не подключено —
`GestureInput.ReadHand()` сейчас всегда читает три клавиши на руку
(верх/середина/низ зоны) как заглушку; подключение реального датчика — это
переписать только тело `ReadHand()`.

Жесты:
- Обе руки вверх → прыжок. Обе вниз → пригнуться.
- Одна вверх, другая вниз → полоса в сторону опущенной руки.
- Тронуть **среднюю** зону обеих рук **одновременно** (< 0.15 с) → газ
  (импульс ~0.3 с). **По очереди** (0.15–0.6 с между нажатиями) → тормоз.
  Дальше 0.6 с — не считается парным жестом.

Клавиши имитатора (верх / середина / низ на каждую руку):

| | левая рука | правая рука |
|---|---|---|
| Левый игрок | Q / A / Z | W / S / X |
| Правый игрок | O / L / . | P / ; / / |

HUD: `GestureIndicator` — по 2 стрелки внизу слева/справа экрана (по игроку),
загораются жёлтым по текущему чтению руки; в режиме клавиатуры остаются
тусклыми (`GestureInput` не крутит `Update`, пока `enabled == false`).

### Дорога, препятствия, тени, спидометр
- 3 полосы, дорога статична, разметка «едет» через скроллинг текстуры
  (`ScrollingTexture`), чтобы не было рывков от пересоздания геометрии.
- `EntitySpawner` спавнит объекты в два шага: хороший/плохой, затем (для
  плохого) — перепрыгнуть или пригнуться. Пока `CurrentSpeed <= 0` — не спавнит.
- Хорошие объекты → `+1` к счёту, плохие → `-1` и краш (переворот игрока,
  временная неуязвимость с миганием, скорость дороги падает вдвое).
- Арка (`DuckUnderObstacle`, 6 цветов) — под ней нужно пригнуться, иначе краш.
- **Тени** (`GroundShadow`, `AddStaticGroundShadow` в `SceneSetup.cs`): у
  игроков — динамическая тень, всегда строго под ними на уровне дороги
  (X/Z следуют за игроком, Y зафиксирован), помогает рассчитывать прыжки. У
  каждого **плохого** объекта (не у хороших, не у луж — те и так плоские) —
  статичная тень, запечённая в префаб.
- **Спидометр** (`SpeedIndicator`) — панель под таймером, текущая скорость.

### Взаимодействие двух игроков на одной полосе
- Игрок не может сместиться на полосу, где уже **стоит на земле** другой
  игрок. Если целевой (или сам двигающийся) игрок в воздухе (прыжок/отскок)
  — перемещение разрешено, один проходит под/над другим.
- Если игрок прыжком оказывается в одной полосе с игроком на земле, и прыжок
  заканчивается, а тот всё ещё там — приземление не происходит: верхний
  «приземляется» на спину нижнего и тут же автоматически отскакивает снова
  (`Bouncing`-состояние), не долетая до дороги, пока кто-то не покинет полосу.
  Держать «вверх» во время отскока — заряженный прыжок повыше (та же высота,
  что у одиночного прыжка, но от спины партнёра), с таймаутом как у обычного
  прыжка (не виснет бесконечно, даже если клавишу не отпускать).
- Если оба игрока одновременно в воздухе в одной полосе (совпавшие прыжки) —
  побеждает по стабильному приоритету (меньший `GetInstanceID()`), чтобы не
  падали на дорогу вместе.

### Трюки (`TricksManager`, `TrickPopup`)
Счётчик — панель по центру справа. Два трюка сейчас:
- **АРКА** — один игрок пригнулся под аркой, другой в этот момент проходит
  над ним по воздуху (прыжок/отскок).
- **КОЛЬЦО** — полный обмен полосами: один игрок пересекает в воздухе, другой
  одновременно проходит понизу, в противоположном направлении.

При засчитывании — всплывающий «+1 ТРЮК: <имя>», летит к счётчику трюков
(мирроринг `ScorePopup`), спавнится в точке события (`ScreenSpaceUtil.WorldToCanvasPoint`),
а не в фиксированной точке экрана.

### Победа и таблица рекордов
При счёте 100 (`WinSequence.TryTrigger`) — кат-сцена: счёт улетает и растёт в
центр экрана, объекты гаснут, столкновения выключаются, ввод глушится,
скорость дороги растёт без ограничений, игроки улетают вдаль, надпись «ВЫ
ПОБЕДИЛИ!». Топ-3 (`HighScoreManager`, `PlayerPrefs`) хранит **минимальное
время до победы** и **очки за трюки** той же сессии (обе колонки движутся
вместе при вставке новой записи). Время идёт через `GameTimer` (не сырой
`Time.time`), с паузами на стартовом экране/меню помощи/диалоге — не в зачёт.

## 4. Архитектура кода — файл за файлом

Синглтоны через `public static X Instance { get; private set; }`,
назначаемые в `Awake()`: `SpeedController`, `ScoreManager`, `HighScoreManager`,
`GameTimer`, `WinSequence`, `TricksManager`, `PauseController`, `HelpController`.

| Файл | Роль |
|---|---|
| `PlayerController.cs` | Главный класс игрока: полосы, прыжок/присед/отскок (state machine `VerticalState`), краш/мигание (`CrashState`), трюки АРКА/КОЛЬЦО, обёртки над клавишами (`UpKeyDown()` и т.п.), которые прозрачно переключаются на `GestureInput`, если тот включён. |
| `GestureInput.cs` | Чтение «датчиков» (сейчас — клавиатурная симуляция), жесты → виртуальные сигналы прыжка/приседа/полосы/газа/тормоза. |
| `GestureIndicator.cs` | HUD-стрелки чтения рук игрока. |
| `SpeedController.cs` | Единая скорость дороги: голосование газ/тормоз, пауза, halve-on-crash, win-boost, фоновая скорость на стартовом экране. |
| `SpeedIndicator.cs` | UI-текст текущей скорости. |
| `EntitySpawner.cs` | Спавн объектов в полосах (хорошие/плохие/над-под). |
| `SideScenerySpawner.cs` | Спавн боковых декораций (деревья и т.п.). |
| `MovingEntity.cs` | Общее движение любого спавненного объекта к камере, самоуничтожение за камерой. |
| `ScoreValue.cs` / `ScoreManager.cs` / `ScorePopup.cs` | Очки за объекты: значение, счётчик+UI, всплывающая анимация «+1»/«-1» к месту, где стоит подобравший игрок. |
| `DuckUnderObstacle.cs` | Маркер арки: пропуск при приседе; `TrickAwarded`-флаг — трюк засчитывается один раз на арку, с какой бы стороны он ни сработал. |
| `TricksManager.cs` / `TrickPopup.cs` | Счётчик трюков + всплывающая анимация. |
| `GroundShadow.cs` | Динамическая тень игрока (следует X/Z, Y фиксирован). |
| `ScreenSpaceUtil.cs` | Мировые координаты → канвас-координаты (для попапов в месте события). |
